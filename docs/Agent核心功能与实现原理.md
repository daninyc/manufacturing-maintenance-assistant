## 2. 为什么这不是自由执行工具的维修机器人

这是受约束的证据编排 Agent。服务端决定调用文档检索及固定只读 SQL，模型只能选择已有证据和建议编号。模型不能编写并执行 SQL、修改权限、打开任意路径或下发设备控制。如此设计便于定位证据来源和授权边界，但能力有限：不推断已确认根因，不将历史维修动作自动转为当前操作建议。

## 3. 权限与检索原理

UserContext 从会话恢复，ResourcePolicy 从权威 SQLite 恢复。有效用户、资源 active、密级足够、部门匹配或明确组织共享必须同时满足。管理员管理动作单独授权，不自动跨部门读正文。外发许可又是独立条件，用户可读不代表可以把数据发给模型。

Chroma 中的标签用于减少候选，不是授权真相。检索后按 document_id 回查权威策略，并检查 policy_version、content_version、chunk_id；残留向量、伪造公开标签或旧版本不能据此获得读取权。过滤后才进行模型候选组装；授权证据不足时拒答，不降低权限补齐。

## 4. 文档发布原理与重要操作

管理员先确认草稿标签，上传 PDF/TXT。服务端限制输入、随机命名原件，使用同一字节快照进行解析和散列。策略先转 indexing，向量写入完毕再复核管理员与期望版本，最后 active。失败关闭读取；两个存储并非一个原子事务，通过状态和版本避免半成品可见。

下线先改权威状态，不能先假设向量已删除。标签更新会改变权限版本，旧块因此失效，需要重新发布匹配版本。该方案以短暂不可用换取边界明确。重试遇到 409 必须刷新版本，不应盲目覆盖。

## 5. 模型输入、输出及三源诊断

问答只把授权证据转换为本次随机编号；模型返回编号，应用从自身映射恢复原文。未知或跨请求编号拒绝，引用须与原文匹配，输出前再次校验身份和策略。Prompt 说明上下文属于数据，不能改变权限；真正的强制边界仍是服务端代码。

诊断先验证设备，查询授权报警与维修记录，再取得授权知识。所有参与资源均需允许外发。模型建议只能从经过 SOP 条件、原文及版本验证的选项中选择，而且建议所需证据必须同时存在。关键未解决报警或疑似冲突标记 human_review；grounded=False 明确不宣称根因已确认。
